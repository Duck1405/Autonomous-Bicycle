Python 3.10.20 — this matters. NVIDIA ships TensorRT Python bindings only for
CPython 3.10 on JetPack 6; there is no other supported version without building
from source.

1) TensorRT bindings — symlink, do NOT use PYTHONPATH:
     SP=/home/mlc/miniconda3/envs/LaneNet310/lib/python3.10/site-packages
     ln -sfn /usr/lib/python3.10/dist-packages/tensorrt                  $SP/tensorrt
     ln -sfn /usr/lib/python3.10/dist-packages/tensorrt-10.3.0.dist-info $SP/

   *** DO NOT set PYTHONPATH=/usr/lib/python3.10/dist-packages ***  [verified]
   That directory contains a STUB numpy/ (it has core/, fft/, ... but NO
   __init__.py). Python imports it as an empty namespace package, so you get:
       AttributeError: module 'numpy' has no attribute '__version__'
   and every real numpy in the env is shadowed, because PYTHONPATH PREPENDS.
   The genuine system numpy is in /usr/local/lib/python3.10/dist-packages.
   The symlink above appends nothing to sys.path and avoids the whole trap.

2) pip packages (from pypi.org, which is reachable) [verified installed]:
     numpy 2.2.6, opencv-python-headless 5.0.0.93, tqdm 4.69.1, onnxruntime 1.23.2

   DO NOT `pip install tensorrt` — NVIDIA does not build TensorRT wheels for
   Tegra ("TensorRT does not currently build wheels for Tegra systems"). apt is
   the only supported route on Orin.

   DO NOT install CUDA from the anaconda nvidia channel. TensorRT links against
   JetPack's system CUDA 12.6. (The anaconda cuda-toolkit link that used to head
   this file is a trap; it is not needed and can only cause version skew.)

   Package index note: pypi.jetson-ai-lab.DEV is DNS-dead [verified: HTTP 000].
   The live one is pypi.jetson-ai-lab.IO (302). Yolov11/jetson_infer_onnx.py and
   Yolov11/README.md still reference the dead .dev host and should be updated.
   Only needed if you ever want torch/onnxruntime-GPU on device — we do not.

3) torch is NOT installed and NOT needed. [verified]
   A tiny FP16 engine was built in memory and executed end-to-end using only

BUILDING ENGINES
--------------------------------------------------------------------------------
  sudo nvpmodel -m 2 && sudo jetson_clocks          # do this first
  cd /home/mlc/aman/Autonomous-Bicycle
  /home/mlc/miniconda3/bin/conda run --no-capture-output -n LaneNet310 \
    python Yolov11/onnx_tensorRT.py \
      --onnx LaneATT/onnxmodels/YoloN/yolo11n_coco4_nms.onnx \
      --fp16 --workspace 1 --timing-cache /home/mlc/aman/trt_timing.cache

onnx_tensorRT.py changes made for this device:
  * --workspace now defaults to 1 GB on Tegra (was a flat 4 GB, sized for an
    A100). CPU and GPU share 8 GB here.
  * --timing-cache added — a retried build skips autotuning it already did.
  * --builder-opt-level added (TRT default 3; lower = faster build).
  * tqdm import is now optional instead of a hard dependency.
  * --hardware-compat is REFUSED on Tegra. NVIDIA documents hardware
    compatibility as unsupported on JetPack/DRIVE OS, so it could only make the
    engine worse.
  * The FP16 error message no longer tells you to `pip install tensorrt` — that
    is impossible on Tegra and sent readers down a dead end.
  * A build returning None now prints cudaMemGetInfo free memory so OOM is
    distinguishable from a real build failure.
  * Every build now writes a <engine>.json sidecar: TRT version, sm arch,
    platform, precision, workspace, build seconds, source ONNX md5.
  * init_libnvinfer_plugins() is called before parsing, so EfficientNMS_TRT-style
    plugin exports parse too.

Build one model per process. The allocator does not fully release between
builds, and on 8 GB that is the difference between finishing and being killed.

Engines are written next to their ONNX (same layout as the cluster).

*** ENGINES DO NOT TRANSFER. *** An engine is locked to the TensorRT version AND
the GPU arch that built it. The A100 engines cannot run here (x86_64 -> aarch64
never works), and these Jetson engines cannot run on the cluster. A JetPack
upgrade that bumps TensorRT invalidates every .engine on the device — that is
what the .json sidecars are for. Prebuilt engines from HuggingFace are useless
for the same reason.

No NaN/Inf anywhere. *** The documented Depth-Anything-V2 FP16 degradation on
this exact stack DID NOT REPRODUCE for our export. *** The forum report showed a

is ever re-exported at a lower opset.

*** MAXN_SUPER IS 1.92x FASTER THAN THE 15W DEFAULT. *** That is the single
cheapest performance win available and it costs nothing but power and a fan.
Decide deliberately which mode the bike ships in. NOTE: the nvpmodel setting is
PERSISTENT ACROSS REBOOTS (stored in /var/lib/nvpmodel/status, not just
/etc/nvpmodel.conf), so setting it once sticks. jetson_clocks is NOT persistent
and must be re-applied each boot if you want it.

The Jetson is 3.8x slower than the A100 end to end, but only 7.1x slower on the
engines and 1.7x on CPU preprocessing. Neither run thermally throttled — 60.7 C
peak against a ~95 C+ limit, so these are sustained numbers, not burst.

*** THE BOTTLENECK INVERTED vs THE A100. *** On the A100, CPU preprocessing was
the bottleneck (7.6 of 14.0 ms = 54%). On the Jetson, the ENGINES dominate
(38.4 of 52.8 ms = 73%) and depth alone is 27.0 ms of that. This changes what
the ROS2 work should optimize — see below.

--------------------------------------------------------------------------------
GOTCHAS THAT WILL BITE YOU
--------------------------------------------------------------------------------
* The numpy stub / PYTHONPATH trap (above). This is the single most confusing
  failure mode in this environment.
* Orin Nano has NO DLA. Ultralytics issue #19302 shows the confusing
  "DLA validation failed" you get for trying.
* Pure-ONNX NonMaxSuppression is a data-dependent-shape op, and TensorRT
  10.0-10.6 has a documented performance regression for DDS ops. JetPack 6.2
  ships 10.3, which is inside that window. yolo11n_coco4_nms.onnx DOES contain
  a real NonMaxSuppression node (opset 13) — see "how to improve".
* Depth-Anything-V2 FP16 on this exact stack (Orin Nano, JetPack 6.2, TRT
  10.3.0.30) has an NVIDIA forum report of badly degraded output, closed with no
  confirmed fix; the usual cause is LayerNorm overflowing in FP16 in ViT
  backbones. GOOD NEWS for us [verified]: our export is opset 17 with 28 native
  LayerNormalization nodes, so TensorRT maps them to its own normalization layer
  instead of decomposing into ReduceMean/Sub/Pow/Sqrt/Div — the configuration
  least likely to overflow. Confirm with trt_vs_onnx_parity.py regardless; never
  trust an FPS number from an engine whose output you have not checked.
* There is a reported L4T 36.4.7 firmware bug ("unable to allocate CUDA0
  buffer"). It does NOT affect this unit [verified: 2 GiB cudaMalloc succeeds,
  4.2+ GiB free]. If large allocations start failing after an apt upgrade, that
  is the bug, not your workspace setting.
* TensorRT docs default to the latest version (11.x), which REMOVED --fp16 and
  --best and renamed flags. Pin doc URLs to 10.3 or just read
  /usr/src/tensorrt/bin/trtexec --help on the device.
* trtexec flag renames since 8.x, if you use it instead of the Python API:
  --workspace=N -> --memPoolSize=workspace:NM ; --buildOnly -> --skipInference ;
  --batch/--maxBatch removed entirely (implicit batch is gone in TRT 10).

--------------------------------------------------------------------------------
HOW TO IMPROVE  (ranked, for the ROS2 work)
--------------------------------------------------------------------------------
Re-ranked against the MEASURED Jetson numbers, not the A100 assumptions.

1. RUN AT MAXN_SUPER. 9.88 -> 18.95 FPS for one command. Nothing else on this
   list comes close to a 1.92x win for that little effort.
     sudo nvpmodel -m 2 && sudo jetson_clocks     # nvpmodel survives reboot

2. Be realistic about what ROS2 parallelism buys. The three models are
   independent, but they contend for ONE GPU, so the engines effectively
   serialize: 38.4 ms of GPU work per frame is a floor no amount of threading
   removes. What parallelism DOES buy is overlapping the 12.7 ms of CPU
   preprocessing and 1.6 ms of decode with GPU execution, i.e.
     52.8 ms  ->  max(engines 38.4, cpu 14.3)  =  38.4 ms  =  ~26 FPS.
   So: pipeline CPU against GPU for ~26 FPS. Getting past ~26 FPS requires
   cutting actual GPU work (items 3-5), not more threads. Budget accordingly —
   "run them in parallel" is worth about +37%, not +200%.

3. Run depth at a lower rate. Depth is 27.0 of the 52.8 ms budget (51%) and is
   the slowest engine by 2x. Scene depth changes slowly compared to lane
   position; running it every 2nd or 3rd frame while lane/object detection stay
   at full rate is the largest single reduction in GPU work available. Combined
   with item 2 this plausibly reaches 35-40 FPS.

4. Test a non-NMS YOLO export with NMS on the CPU. We already have the raw
   yolo11n on device (output0[1,6,8400]). The NMS variant contains a real
   NonMaxSuppression node, and TensorRT 10.0-10.6 (we run 10.3) has a documented
   data-dependent-shape performance regression. Cheap to test: ~7 min to build.
   Note the NMS build also took 437 s versus LaneATT's 45 s, which is consistent
   with the DDS ops being hard to autotune.

5. Try INT8 if items 2-4 are not enough. The FP16 parity results are excellent
   (corr >= 0.999999), which suggests headroom, but INT8 needs a calibration set
   and a fresh parity run — do not ship it on faith.

6. --builder-opt-level 4 or 5 for models you build once and ship. Slower build,
   better tactics. Use the timing cache so retries are cheap.

7. GPU-side preprocessing matters LESS here than on the A100 — it is only 12.7
   of 52.8 ms, and item 2 already hides most of it behind GPU work. Do this
   after 2-4, not before.

8. Going headless (systemctl set-default multi-user.target) frees ~0.8-1 GiB.
   NOT NEEDED — peak RAM during the benchmark was 3390/7620 MB and builds never
   touched swap. Keep the desktop.
